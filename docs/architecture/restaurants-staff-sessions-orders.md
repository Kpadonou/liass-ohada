# LR-TX-1 — Staff Sessions & Order Foundation

Classification: `VERTICAL_SOLUTION`; owner: Restaurants. The approved contract remains [restaurants-transactional-access-patterns.md](restaurants-transactional-access-patterns.md), frozen at `f06ef03`. This note records implementation details without changing that contract.

## Release scope

GuestSession, Order, OrderItem, bounded submission rounds, base-table locators, immutable audit/activity and durable command replay are implemented in the dedicated Restaurants table. Existing configuration keys, setup/menu/QR APIs and Platform ProductAccess ownership are preserved.

This is a **dev foundation**, not a complete operational food-service release. RESTO-PREP-1A adds backend Preparation tasks and station queues as described below; Kitchen UI, payments, receipts, providers, public guests and table transfer/merge remain deferred. Positive-price orders cannot settle until the payment phase. Historical station-routed accepted lines cannot close merely because preparation is absent. The original LR-TX-1 phase introduced no staff administration or fabricated outlet assignment.

Table Workspace prioritizes Menu browsing, the current draft and immutable accepted-round summaries, with no Kitchen state inferred from commercial acceptance.

Its contextual `/restaurants/service/outlets/:outletId/sessions/:guestSessionId` route supports reload and deep links without global session state or a sidebar destination. Keyed session authorization is independent of order permissions. RESTO-TABLE-1A established the session summary foundation. Local state-tab switches make no requests. Pending/error feedback stays on the task, ambiguous retry keeps the same request identity, and normal refetch retains authorized board content. Future polling/combined reads require operational evidence rather than automatic expansion.

## Operational Carte read contract

The technical `Menu` is the outlet's canonical sellable Carte/catalogue, with one singleton Menu per outlet. “Menu du jour” is a distinct future concept. Categories remain canonical configuration metadata; operational order-taking need not navigate them. `GET /restaurants/outlets/{outletId}/menu/items` uses the existing `RESTAURANTS_MENU_READ` permission, preserving all currently authorized roles (including existing CASHIER/KITCHEN menu reads), without granting Order commands or service authority. Active Restaurant/outlet/Menu are required; absence is the existing 404, inactive parents the existing 409.

The unified operational response contains `outletId`, `menuId`, `items` and optional `nextCursor`. Rows expose existing item `id`, name, version, categoryId/categoryName, configured price/currency, availability and outlet/Menu identity. Inactive items or categories are omitted; active UNAVAILABLE items remain visible for disabled presentation. Commercial Add/submission validation remains authoritative for current sale eligibility. No accepted sale snapshot is repriced.

One request performs three canonical parent GetItems, one strongly consistent Query of `PK=ORG#<orgId>`, `begins_with(SK, ITEM#<outletId>#)`, and zero or one BatchGet of distinct candidate categories (at most 100 keys). Hydration reuses the bounded batch helper: retry only unprocessed keys, three attempts total, then temporary failure; missing/corrupt ownership fails closed. Default/max physical Query limits are 50/100; DynamoDB's 1 MB boundary also applies. No GSI, projection, write maintenance, Scan or migration is introduced. Pagination is a live collection, not a multi-request snapshot. Ordering is existing category-ID then item-ID sort-key order, not configured category position or name ranking. The Menu identity and normalized q bind the opaque cursor with organization/outlet and versioned collection semantics.

**Bounded search V1 limitation:** optional `q` filters only the current physical Query page after reading it; it is not indexed global search. Normalization is shared through `normalizeMenuItemSearch`: NFD, Unicode mark removal, lowercase, non-letter/digit boundaries and collapsed whitespace. Every normalized query token must prefix some normalized name token (AND semantics, order independent); no arbitrary substring/fuzzy search. Display names remain unchanged. Empty/whitespace q browses normally; nonempty normalized q requires at least two characters, raw input is at most 160. `Café` matches `cafe`, `Poulet braisé` matches `pou`/`bra`, `Jus d’ananas` matches `ana`. The operational frontend now uses the same normalized token-prefix/AND semantics through a memoized token representation.

Operational search is local-only over cached canonical rows. Never send `q` as global completion: the existing endpoint filters physical pages and cannot provide indexed completion. Absence of a next cursor establishes exhaustion of the current sequential traversal, not snapshot isolation against concurrent catalogue edits. Indexed search/projection/backfill remains deferred until measured scale justifies a separate approved lot.

### Full-Carte caching feasibility (RESTO-MENU-CACHE-0A)

The CACHE-0A reconnaissance selected **B — hybrid threshold**; CACHE-1A now implements this frontend strategy: use background full-cache/local search within a finite V1 client budget and defer indexed backend search until observed scale requires it. Schema-validated Node 22/arm64 measurements gave 318-byte small rows, 328–376-byte representative rows (349-byte mean), 977-byte long Unicode rows and a 2,257-byte escaped contract extreme. Representative 300/500-item responses total about 103/172 KiB over 3/5 physical pages at limit 100; 2,000 items about 690 KiB/20 pages. These nominal counts assume one eligible item per evaluated record; inactive rows, filtered categories and DynamoDB's 1 MB boundary can require more pages. Browser object memory is estimated at 3–6 times JSON plus derived tokens and transient refresh copies, not measured heap. A disposable Node benchmark (200 iterations after warmup) measured shared-matcher median filtering around 0.14/0.69/1.38/2.82 ms for 100/500/1,000/2,000 rows, versus approximately 0.005/0.010/0.019/0.037 ms with derived pre-normalized tokens. These are synthetic local measurements, not mobile/rendering guarantees.

Proposed automatic hydration budget: at most 20 physical pages and approximately 2 MiB cumulative uncompressed response JSON per outlet generation, stopping at page boundaries (one bounded-page payload overshoot is possible). This covers the measured 2,000-item realistic scenario while bounding requests even when most evaluated items are filtered out. It is a client safety threshold, not a domain cap or proof of live Menu cardinality. Repeated budget exhaustion, unacceptable hydration latency or mobile memory/render measurements would justify revisiting indexed search. At budget exhaustion/error, retain useful loaded rows and an explicit incomplete/continue-or-retry state; never declare global no-results. No new count query or percentage is needed. Do not automatically traverse beyond the budget. Indexed search beyond this envelope requires a separate approved lot; no projection/backfill is authorized here.

CACHE-1A owns canonical pages in TanStack Query under `['restaurants', orgId, 'operational-carte', userId, contextRevision, outletId, menuId, 'browse-v1']`. GuestSession/table/category/search text are excluded. Menu identity reads are likewise outlet/principal/revision scoped. Fresh data is reused across tables and A → B → A outlet navigation. Root-prefix eviction, abortable HTTP, before/after principal/revision checks and DTO ownership validation preserve tenant safety; outlet changes stop old hydration scheduling.

Pages use limit 100, five-minute staleTime and fifteen-minute inactive gcTime. Stale mount/focus/reconnect and explicit refresh reconcile canonical data; there is no polling. A coherent refresh follows a new cursor chain and atomically replaces the old traversal, with no new-head/old-tail mixing. Automatic traversal, including refetch of a previously extended cache, stops at 20 physical pages or approximately 2 MiB response JSON. A page-boundary overshoot is possible. Explicit continuation grants another bounded tranche. Empty physical pages count against the budget. Canonical last-page nextCursor, rather than a scheduler stop, determines exhaustiveness.

One next page is hydrated at a time only while observed, authorized, visible and online. A transient HTTP failure retries once, then preserves successful pages with local continuation/retry; authorization/configuration failures do not retry automatically. Partial search never claims definitive no-results. Tokens are derived once per canonical-data update; all cached rows are searched, while browse/search DOM starts with 50 matches and expands by 50. Category remains subdued canonical metadata, with no operational category navigation. Management Menu/category/item mutations invalidate only the affected outlet Carte; ordinary Order mutations do not. Cached Menu prices/versions never replace Add/submission validation or accepted snapshots. No prefetch, virtualization, indexed search or media capability is introduced. Deterministic review fixtures include both FREE and OCCUPIED tables and multi-page/failure/budget scenarios.

## Preparation foundation (RESTO-PREP-1A)

Commercial submission and preparation are separate dimensions. Order lifecycle remains DRAFT/SUBMITTED/CLOSED/CANCELLED; it never implies kitchen execution. The immutable accepted OrderItem snapshot is commercial authority. A canonical Preparation task is operational authority; a station lane is a typed read projection. There is no mutable Kitchen Ticket aggregate. Grouping by submission and station is presentation only.

Submission creates one full-quantity generation-1 task and QUEUED projection for each newly accepted station-routed line in the same transaction as sale snapshots, Submission, Order/GuestSession financial summaries, audit and replay. Routing uses the validated accepted station ID/version; old tasks are never rerouted from current Menu. No-station lines create no task/counter and are immediately service-eligible. Additional rounds create work only for new drafts. Twelve distinct routed lines require 83 actions before scoped waiter guards (87 with the existing four staff/membership guards), below the unchanged 90-action limit; byte/item limits remain authoritative. New submissions still require active sale/station configuration.

Approved Preparation V1 authorization is outlet-wide: active KITCHEN RestaurantStaff with active requested-outlet assignment and active membership/ProductAccess/outlet may read and start/ready work across all stations in that outlet. No station-specific staff assignments exist or are inferred. OWNER/MANAGER retain organization-level operational authority without Staff requirements. Explicit permissions are PREPARATION*READ, PREPARATION_START_MANAGE, PREPARATION_READY_MANAGE and PREPARATION_SERVE_MANAGE, each prefixed RESTAURANTS*. OWNER/MANAGER receive all four, KITCHEN the first three, WAITER only SERVE, CASHIER/invalid roles none. WAITER kitchen queue/Order preparation reads remain denied pending a separate service-read decision. These grants do not grant Order reads/mutations, configuration management, payment or exception rights. Responsible staff and Order.waiterId are not security boundaries.

Task lifecycle is QUEUED → IN_PROGRESS → READY → SERVED. Explicit POST commands require clientRequestId and expectedVersion; no arbitrary status PATCH exists. Every command reauthorizes before durable replay. Each successful transition atomically replaces the versioned task, removes its old versioned lane membership, creates the next membership when nonterminal, checks the current accepted line/latest fire and nonterminal Order, and writes existing audit/activity/replay records. Serve decrements outstandingWorkCount under the Order version condition. Start/ready do not write GuestSession or financial summaries. No preparation transition changes sale quantity/prices/currency, Order due or GuestSession due. Active outlet/staff/membership/ProductAccess guards participate in command transactions to reject intervening revocation.

RESTO-KITCHEN-0A separates operational self-outlet discovery from Service Floor. Discovery grants no Service Floor, GuestSession, Order or Preparation authority. Kitchen V1 work remains outlet-wide across stations under independent Preparation permissions and active outlet assignment; station-specific assignment is deferred. This foundation adds no Kitchen navigation or discovery UI.

No re-fire endpoint is implemented: fireId/generation and bounded line latestFireId/fireCount preserve the frozen future design. No historical accepted lines are automatically backfilled or presented as queued.

Existing accepted tasks remain readable/actionable after their station is deactivated, provided current outlet authorization remains valid. Their snapshotted station identity is retained. Staff/outlet assignment deactivation denies subsequent reads/commands and replay, without rewriting historical work.

Physical paths use only additive KeyFactory helpers, with S = ORG#{orgId}#OUT#{outletId}: canonical tasks use PK S#ORD#{orderId}, SK PREP#{itemId}#{fireId}; typed memberships use PK S#WORK#{stationId}#{QUEUED|IN_PROGRESS|READY}, SK {queuedAt}#{orderId}#{itemId}#{fireId}. ## Atomic behavior

Opening a session writes its META, conditionally absent table pointer, active and two history locators, audit/activity and command replay. Closing requires OPEN, matching version, no open orders, settled balance and no reserved/pending payment. Only its own occupancy pointer is released; history remains.

DINE_IN requires an OPEN session, deriving table identity from that session. COUNTER and TAKEAWAY are standalone and do not create synthetic sessions. Session-linked creation atomically adds order META, active/history locators, both session links, session counters, audit/activity and replay. Session order count is capped at 50; each order at 200 retained lines.

Draft creation/editing changes versions and counters without charging money. Submission accepts at most 12 selected drafts, checks reviewed menu-item versions, resolves active configuration and freezes immutable accepted snapshots. Quantities and minor amounts are checked safe integers; multiplication/addition use checked arithmetic. Discount/tax fields are zero support placeholders, not a tax-exemption claim.

Historical LR-TX-1 submission wrote `n` accepted lines plus Submission, Order META, order audit, activity and replay; conditionally added unpaid membership; linked orders also updated GuestSession META and session audit. Configuration checks were deduplicated for root/outlet/menu/categories/items/stations. Its linked 12-line case was **59 actions**, without PREP/WORK. RESTO-PREP-1A adds the task/queue writes described above. Independent guards still enforce at most 90 actions, at most 3 MiB of serialized marshalled transaction payload and less than 350 KiB per put item; these conservative limits do not establish measured production capacity.

Accepted-item cancellation retains the original sale snapshot and records actor/time/reason, subtracts contribution once and atomically updates order/session totals and unpaid membership. Paid/reserved/pending invariants remain protected. Whole-order cancellation is deliberately bounded: cancel individual draft/chargeable lines first until no drafts or debt remain, then finalize cancellation. It never updates an unbounded 200-line collection in one transaction. Close requires SUBMITTED, an accepted line, no drafts, settled debt and no financial/preparation blockers. A zero-price non-station sale can close; a positive unpaid order cannot. Sessions never close automatically.

Each externally retryable mutation accepts a UUID `clientRequestId`. Lookup hashes tenant/outlet/command/owner/request identity independently of the normalized intent fingerprint. A successful transaction stores generated IDs and its original result. Authorized identical retries replay that result; changed intent conflicts. Failed validation has no durable side effect. Canonical version conditions and configuration checks protect concurrent edits and price changes.

## Scoped cashier checkout reads (RESTO-CHECKOUT-1A)

`RESTAURANTS_CHECKOUT_READ` is a read-only grant for OWNER, MANAGER and CASHIER. It is an alternative entry permission on the existing Service Floor, keyed GuestSession, session Orders, keyed Order and OrderItems handlers only. Primary service permissions and the API route registry are unchanged. CASHIER also receives `RESTAURANTS_STAFF_OUTLET_SELF_READ`; WAITER/KITCHEN self-discovery and management discovery retain their existing boundaries.

A CASHIER read rechecks direct active membership, active Restaurants ProductAccess, current role, ACTIVE RestaurantStaff, ACTIVE requested-outlet assignment and active outlet on every request, using RestaurantServiceAccess. Keyed checkout content requires a canonical OPEN DINE_IN GuestSession in that organization/outlet; keyed Orders must reference that session and its table. Responsible staff is metadata, not authorization. OWNER/MANAGER retain existing broader reads without Staff requirements. WAITER and KITCHEN grants are unchanged. Neither checkout read nor self-discovery authorizes opening, responsibility assignment, Order/draft mutations, submission, cancellation, Preparation, SERVE, payments or closure.

The existing bounded Service Floor may return FREE rows as well as OCCUPIED candidates; the future checkout UI derives occupied candidates locally. Session detail uses the GuestSession table-name snapshot and existing financial counters (`dueMinor`, `paidMinor`, `reservedMinor`, `pendingPaymentCount`, `orderCount`, `openOrderCount`). Operational presentation uses the table NAME; existing compatible DTO table-code fields remain technical metadata. No redundant balance field is added: unpaid is due minus paid, and available payment capacity is due minus paid minus reserved.

Cashier OrderItems pages expose only lines with accepted commercial snapshots, including accepted cancellations. Draft content is excluded; `Order.draftLineCount` signals unresolved drafts. Filtering occurs within the existing bounded physical page: an empty result can still carry `nextCursor`, which must be followed before claiming exhaustion. Snapshot amounts, names and submission identities remain authoritative. No line or monetary mutation occurs. CLOSED-session content and standalone COUNTER/TAKEAWAY Orders remain outside this operational grant; standalone checkout/history require a separately reviewed read boundary.

Existing opaque cursor scope/order and limits remain: default 50/max 100, at most 50 Orders per session and 200 retained lines per Order. Session Orders hydrate at most one bounded page of distinct Order metadata with existing concurrency eight; OrderItems use one bounded Query per page, never per-line requests. No new keys, GSI, Scan, projection, migration or resource is introduced.

For one page of each collection and one items page per Order, cold HTTP composition costs `4 + N`: self-outlets, floor, session, session Orders, then N item pages (5/7/14 requests for 1/3/10 Orders). With discovery already cached, detail costs `2 + N`; session Orders already contain Order metadata so separate keyed Order calls are unnecessary. Integration fixtures with no responsible-staff attribution measure 50/76/167 GetItems, 4/6/13 Queries and four BatchGets respectively, including repeated per-request authorization. These are fixture measurements, not universal caps: responsible-staff enrichment, additional pages and bounded BatchGet retries add reads. At max page size, 200 retained lines require at most two item pages per Order (four at the default); 50 Orders imply at most 100/200 item-page requests, traversed explicitly with bounded concurrency rather than automatic uncontrolled fan-out.

Future TanStack queries should reuse fresh self-outlet/floor/session/Orders data, scoped by principal/context revision, organization, outlet and session/Order identity. Checkout reads do not invalidate catalogue caches. Authorization revocation always takes effect on the next server request. There is no Restaurants Payment/history entity or capture/closure grant in this lot.
