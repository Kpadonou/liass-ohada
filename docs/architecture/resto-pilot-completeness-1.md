## Pilot definition and verdict

Configure → open service → take order → send to kitchen → prepare → serve → checkout → produce commercial/payment proof → manage cash → close business day → observe stock state.

**B. READY AFTER P0 FIXES.** The nominal DINE_IN chain is implemented. The architecture already supports safe correction and abandonment commands, but current operator surfaces do not expose essential accepted-item/order cancellation. An ordinary emptied draft Order can prevent table release. This is an application handoff gap, not a fundamental absence of ordering/payment/cash infrastructure. Two remediation chantiers cover the repeated blocker scenarios below. A controlled pilot must also agree the P1 operating procedures and pass focused multi-role DEV and Product Owner acceptance. This verdict does not declare launch approval or country fiscal compliance. Refund 1E/1F remain CLOSED.

The pilot is not feature-complete restaurant ERP. It assumes online operation, an existing entitled organization/active Outlet, OWNER-assisted staff provisioning, configured stations for prepared items, and Inventory Lite restricted to supported discrete unprepared items. A one-time bootstrap operation and a physical count are not parallel order/ticket/payment systems. An essential technical operator needed to correct live orders is unacceptable.

## P0 — PILOT BLOCKERS (ranked distinct gaps)

### 1. RESTO-PILOT-CANCELLATION-1 — Accepted-line operational correction

- **Exact gap:** no accepted-line cancellation action in the service workspace/history, including management use. `restaurant-orders.api.ts` exposes create/add/edit/remove/submit; the composer `remove()` checks `DRAFT`, and accepted service history has no mutation action. KDS offers start/ready only. A status enum is not evidence of operator access.
- **Why blocking:** wrong accepted item, changed mind or kitchen inability leaves an unwanted charge/work item unless a technical operator invokes an API. Staff cannot preserve accurate kitchen intent and checkout through the app. Covers matrix E/F/G and the three Kitchen cancellation phases.
- **Existing architecture:** `transaction-service.ts` CANCEL_ITEM branch (~1281) accepts management cancellation, freezes reason/actor, adjusts commercial/session totals, preserves paid/reserved limits and invokes Preparation cancellation plus original stock reversal. Scoped WAITER can cancel only DRAFT. `preparation-service.ts` cancellation (~112) handles active states including IN_PROGRESS and READY, decreases outstanding work once; SERVED is already terminal. No new business truth is needed.
- **Smallest remediation:** manager-only accepted-line action/dialog with explicit reason and confirmation, existing expected versions and stable request UUID; refresh affected service/bill/preparation caches. Retain immutable source, safe payment constraints and partial service. Do not grant KITCHEN/WAITER financial cancellation implicitly. No new GSI, projection or broad API is indicated.
- **Scope/dependency:** frontend/data-access composition and focused integration tests; backend/domain guard changes only if a separately approved role requirement demands them. Depends on current cancellation routes and fresh canonical data. A partially paid sale may be non-cancellable under current due/paid guards; finalized correction follows CreditNote/Refund rather than deleting payment truth.
- **PO decision:** approve manager escalation as pilot policy, cancellation authority/reason and handling of prepared-but-wasted goods. Delegating cancellation to WAITER would be a separate authorization decision, not required for this smallest fix.

### 2. RESTO-PILOT-ABANDONMENT-1 — Empty/abandoned Order resolution and service release

- **Exact gap:** no app action for management CANCEL_ORDER, or composed cancellation of a whole order/round. A persisted Order whose drafts were all removed remains nonterminal. `transaction-service.ts` (~1324) rejects CLOSE for never-accepted DRAFT; CLOSE_SESSION (~1049) requires zero open Orders. Checkout only closes, never cancels.
- **Why blocking:** a common abandoned draft can leave a table occupied indefinitely through normal UI. Charging a fictitious item or directly changing counters is not an acceptable workaround. Covers H/I; true corrupt residual state remains a distinct guarded recovery concern.
- **Existing architecture:** CANCEL_ORDER already safely finalizes an unpaid, unreserved, no-draft, no-outstanding-work order. Cancel individual lines first where required, then cancel Order, then normal versioned GuestSession closure. No dedicated round aggregate/command was found; a round is a submission and its lines.
- **Smallest remediation:** manager action for an empty Order, bounded multi-step abandoned-order flow using existing line/order commands, visible partial progress, fresh reads and explicit final service closure. Cancellation of multiple Orders must preserve successful prior steps. Do not auto-release on payment or introduce force-unlock.
- **Scope/dependency:** frontend/domain-command adapter and tests; existing backend sufficient for described unpaid states. Depends on P0-1 for accepted lines. Proof: `checkout-closure.test.ts`, “drafts are retained and empty never-accepted draft requires existing management resolution”; current cashier cancellation returns 403.
- **PO decision:** approve manager escalation and explicit abandonment semantics. No permission widening or automatic removal of drafts is necessary.
