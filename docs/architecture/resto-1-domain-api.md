# RESTO-1A / RESTO-1B — Restaurants configuration and API

## Boundaries and ownership

`RESTAURANTS` is an independent product. Domain owner: `lambda/domains/restaurants`; public contracts: `@liass-ohada/shared/restaurants`. Organization remains the platform tenant/legal identity. Restaurant is a separate operational root, exactly one per organization for this phase; it owns many Outlets. Outlets own ServiceAreas, Tables, PreparationStations and exactly one Menu. Menus own Categories; Categories own Items. Parent IDs are immutable; moving an entity is outside this phase. A table belongs to exactly one area and outlet. A preparation station is configuration only, without kitchen behavior.

One Menu per Outlet makes optional station references local to the same operational site. Menu currency is immutable, and prices use safe nonnegative integers in minor units with an explicit three-letter currency code. The repository exposes no product-neutral Money object; the existing safe-integer/minor-unit convention and three-letter currency format are retained without importing SALES-owned schemas. No SALES catalog, invoice, order or payment abstraction is reused. Zero/complimentary prices are allowed. No recipes, ingredients, inventory, cost calculation, guest/session/order/payment behavior, fiscal integration or frontend setup is included.

GuestOrderingPolicy is stored on Restaurant: DISABLED, STAFF_APPROVAL (default), DIRECT. It configures future behavior; it creates no guest API. MenuItem availability AVAILABLE/UNAVAILABLE is independent of historical isActive. guestReorderEnabled defaults false and describes future eligibility only.

## Public contracts

Strict Zod entity, create, update, lifecycle, list and response schemas expose logical IDs and metadata (name, isActive, version, createdAt, updatedAt). They expose no physical keys, entityType or tenant identity. Create requires clientRequestId UUID. PATCH requires expectedVersion and at least one mutable attribute. Parent IDs are validated UUID route context, never mutable attributes. Optional table capacity is positive <=1000; null clears capacity. Null clears an optional item station assignment. Names are trimmed, nonempty, <=160 characters. Codes normalize to uppercase and allow 1–32 alphanumeric/underscore/hyphen characters. Reads include inactive historical records. No physical deletion is exposed.

The platform wrapper ignores body orgId/userId consistently with existing APIs; schemas themselves reject these attributes. The authoritative organization is verified x-org-id, and actor identity is Cognito sub. RESTO-1C must use the shared response schemas and tenant-scoped query keys.

## DynamoDB item model and access patterns

All concrete keys below are generated by KeyFactory. Existing keys remain unchanged. No new table/index is required.

| Item | PK | SK / collection prefix | Access |
|---|---|---|---|
| Restaurant | ORG#orgId | RESTAURANTS#ROOT | GetItem singleton |
| Outlet | ORG#orgId | RESTAURANTS#OUTLET#id | GetItem / Query prefix |
| ServiceArea | ORG#orgId | RESTAURANTS#AREA#outletId#id | GetItem / Query by outlet |
| Table | ORG#orgId | RESTAURANTS#TABLE#outletId#areaId#id | GetItem / Query by area |
| Table code reservation | ORG#orgId | RESTAURANTS#TABLE_CODE#outletId#CODE | Conditional transaction only |
| PreparationStation | ORG#orgId | RESTAURANTS#STATION#outletId#id | GetItem / Query by outlet |
| Menu | ORG#orgId | RESTAURANTS#MENU#outletId | GetItem singleton |
| Category | ORG#orgId | RESTAURANTS#CATEGORY#outletId#id | GetItem / Query by outlet menu |
| Item | ORG#orgId | RESTAURANTS#ITEM#outletId#categoryId#id | GetItem / Query by category |
| QR lookup | RESTAURANTS_QR#sha256(token) | LOOKUP | GetItem by opaque token |

Configuration records contain PK, SK, uppercase entityType, orgId, createFingerprint and nested `data` validated with the public entity schema. Tables additionally retain private qrToken. Code reservations contain orgId/outletId/tableId. QR mappings contain orgId/restaurantId/outletId/serviceAreaId/tableId; they never appear in DTOs. These persistence-only shapes remain backend-only.

Every Query uses exact organization partition + begins_with collection prefix, consistent read and Limit 1–100 (default 50). No FilterExpression, GSI, Scan or loading of whole partitions. Pagination encodes a logical last ID and SHA-256 scope (org/kind/parents), rederives the key, and rejects another tenant/collection cursor. Ordering is deterministic by key/ID, not business name/position; clients may sort a loaded page. Reads load a bounded parent chain to validate ownership. Exact rows validate stored orgId, type, physical key, ID and parent IDs. Missing or mismatched relationships fail closed.

## QR identity, consistency and retries

Table tokens use crypto.randomBytes(32), base64url (256 bits, 43 characters). Tokens do not encode organization/table IDs. Lookup keys hash the token; all are KeyFactory keys. The administrative GET table/qr requires SETUP_MANAGE and returns only the token. Ordinary DTOs never contain it. There is no public QR endpoint or rotation API. The internal resolver proves direct lookup plus active Restaurant/Outlet/Area/Table checks; it is not registered in HTTP. Unknown/stale mapping, wrong identity or inactive table cannot resolve. Configuration audit logs omit tokens and internal IDs.

Table creation atomically writes table + per-Outlet normalized code reservation + globally unique QR mapping, with conditional absence on all three and parent version/isActive ConditionChecks. A collision rolls the entire transaction back and returns 409; the client may retry. No orphan table/lookup or mapping overwrite is possible. Codes are unique across all areas in one outlet. Deactivation keeps table, QR and reservation; code rename atomically reserves the new code and releases the old reservation after checking ownership. Renaming never changes QR identity.

Entity IDs are custom UUIDv8 values derived from SHA-256(org, kind, immutable parent context, clientRequestId). The normalized create payload fingerprint is retained on the row. Identical network retries return the existing current entity, including the same table token; changed intent under the same request identity returns 409. Singleton Restaurant/Menu conditional keys prevent a second root/menu even with another request ID. No parallel idempotency ledger. Different parent contexts give different IDs. Mutations use expectedVersion, conditional type/org/id/version checks and versioned parent checks in the same transaction, preventing concurrent parent deactivation from accepting a new/updated child. Updates are not automatically retried with a changed version. Deactivation is idempotent at the current version and preserves historical links. No automatic cascade: inactive parent prevents active operational mutations/resolution; historical reads remain available.

## Authorization and API

Every route uses the existing createHandler chain: JWT sub → verified x-org-id/workspace membership → active RESTAURANTS ProductAccess → exact RESTAURANTS permission → service ownership/validation → repository transaction. No frontend visibility is trusted. Global organization OWNER, cabinet access, ACCOUNTING and SALES roles never imply restaurant permissions. Existing scoped productRoles.RESTAURANTS stores roles without a new identity/entitlement model.

| Role | READ | SETUP_MANAGE | MENU_READ | MENU_MANAGE |
|---|---|---|---|---|
| OWNER / MANAGER | yes | yes | yes | yes |
| WAITER / CASHIER / KITCHEN | yes | no | yes | no |
| Absent / invalid role | no | no | no | no |

The canonical executable inventory is `restaurant-routes.ts` (38 routes), reused by CDK; each thin handler embeds explicit product and permission metadata. Existing wrapper conventions return HTTP 200 for successful create/update, translated message + data for mutations, data envelope for individual reads, items/nextCursor for lists, token for QR. Missing entities/foreign parents: 404; access/RBAC: 403; invalid input/currency: 400; version/uniqueness/inactive parent: 409.

Setup reads use RESTAURANTS_READ; setup mutations and QR use RESTAURANTS_SETUP_MANAGE. Menu reads use RESTAURANTS_MENU_READ; menu mutations use RESTAURANTS_MENU_MANAGE. No permission from one product satisfies another.

## Infrastructure and validation

RestaurantsApiStack is the durable owning nested stack for this coherent domain and its expected growth, using RestaurantsEndpoints and DomainConstructFactory. Routes, Lambda integrations/functions/permissions stay there. Existing API Gateway, Cognito authorizer/pool, shared Lambda role, DynamoDB table, secrets and logs convention are reused. No persistent resource moves, no data migration or deployment in this phase. Local synthesis gives API core 277 → 278 and RestaurantsApiStack 0 → 153 (38 each Lambda functions, JWT routes, integrations and permissions, plus one CDK metadata resource). Existing Accounting 51, Identity 81, Sales 161, Fiscal Compliance 41, Projects 12, Treasury 11, Data 4 and root 1 are unchanged. All ten templates remain <=350. Local comparison finds no removed resources or changed shared stateful resources. Shared permission/i18n changes update only Code/asset metadata on 150 existing functions (Accounting 50, Sales 37, Identity 32, Projects 11, Treasury 10, Fiscal Compliance 10); no function configuration changes. The six existing nested template URLs also change. Counts and local template comparison are recorded in the final validation report; cloud cdk diff is intentionally not run because the task prohibits external calls.

The in-memory SDK harness executes actual GetItem/Query/TransactWriteItems inputs and conditional expressions atomically. It is a unit-test substitute for DynamoDB, not an AWS/localstack integration. The deterministic fixture is built through production services/repositories: Héritage Bistro, Agla, Main Room/Terrace, T01–T04, KITCHEN/BAR, STAFF_APPROVAL; Main Dishes/Drinks/Desserts; Grilled Chicken/Fried Plantain (KITCHEN, reorder false), Water/Beer (BAR, reorder true), Chocolate Cake (no station, reorder false). QR values intentionally stay random. Tests prove reads, bounded access, tenant/parent isolation, role denial, uniqueness, version guards, idempotency, QR atomicity/collision and lifecycle.

Stop after RESTO-1B. RESTO-1C frontend and RESTO-1D integrated acceptance remain future work. Fiscal Compliance remains suspended; resume at S4C-0B1 only when separately authorized.
